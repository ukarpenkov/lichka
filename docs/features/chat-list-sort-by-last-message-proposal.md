# Сортировка чатов по последнему сообщению

**Статус:** implemented

## Описание проблемы

Список чатов (`ChatListScreen`) упорядочивается через `getChats()` по `chats.updated_at DESC`. Поле `updated_at` обновляется при создании чата и при правке метаданных (title / avatar), но **не** при отправке сообщений.

Из-за этого:

- пользователь пишет сообщение в чате «Б» и возвращается на список — чат «Б» остаётся на прежнем месте;
- запланированные reminder / alarm с `scheduled_at` в будущем косвенно не влияют (сообщения не трогают `chats.updated_at`), но и реальная активность в чате тоже не влияет;
- анимация `Layout.springify` в `ChatListItem` почти не проявляется: порядок массива при focus-refresh меняется редко.

Ожидаемое поведение (как в мессенджерах): самые свежие по **фактически доставленным** сообщениям чаты — сверху.

## Предлагаемое решение

### Сортировка

Изменить SQL в `getChats()` (`entities/chat`):

- ключ сортировки = `MAX(created_at)` среди сообщений чата, которые уже «доставлены»;
- критерии «доставлено» — те же, что у `getVisibleMessagesByChatId`:
  - `type != 'periodic'` (шаблоны periodic не участвуют; display-сообщения синтетические);
  - `scheduled_at IS NULL` **или** `scheduled_at <= now` (будущие reminder / alarm не поднимают чат);
- если подходящих сообщений нет — fallback на `chats.created_at`;
- смена аватара / названия **не** меняет порядок сама по себе (`updateChat` по-прежнему пишет `updated_at` для import merge, но список по нему не сортируется).

### Анимация

- В `ChatListItem` оставить `layout={Layout.springify().damping(22).stiffness(180)}`.
- В `ChatListScreen` заменить `FlatList` на `Animated.FlatList` из Reanimated и добавить `itemLayoutAnimation` с теми же spring-параметрами.
- При возврате на список после нового сообщения порядок меняется → строки плавно переезжают.

### Пользовательские сценарии

1. Пишет сообщение в чате «Б» → назад → «Б» анимированно поднимается вверх.
2. Меняет аватар чата «А» → порядок не меняется (если не было новой доставки); Layout сработает, если порядок всё же изменился по другой причине.
3. Ставит reminder на завтра → чат не поднимается, пока `scheduled_at` не наступит.

## Влияние на архитектуру (FSD)

| Слой | Изменение |
|------|-----------|
| `entities/chat` | SQL `getChats()` — единственный источник порядка |
| `pages/chat-list` | `Animated.FlatList` + `itemLayoutAnimation` |
| `features` / `widgets` | без изменений |
| `shared/db` | без новой миграции / колонок |

Зависимости только вниз: pages читает entities, как сейчас. Public API `getChats(): Chat[]` не меняется.

## Альтернативы

| Вариант | Плюсы | Минусы | Решение |
|---------|-------|--------|---------|
| A. SQL subquery по delivered messages | Корректно без денормализации; совпадает с visible rules | Чуть тяжелее SELECT | **Выбран** |
| B. Denormalized `last_message_at` + touch при createMessage | Быстрый ORDER BY | Нужна миграция, все точки записи, риск рассинхрона | Отклонён |
| C. Сортировка в JS на экране | Гибко | Дублирует бизнес-правила вне repository | Отклонён |
| D. Сортировать по `updated_at` + bump при сообщении | Простой touch | Future scheduled с `created_at = scheduled_at` легко ошибочно bump'нуть | Отклонён |

## Оценка сложности

- **Время:** ~1–2 часа (SQL + FlatList + тесты + docs).
- **Риски:**
  - Layout-анимация FlatList зависит от Reanimated `itemLayoutAnimation` — параметры выровнены с `ChatListItem`.
  - Periodic display-fires не влияют на порядок до появления отдельной денормализации (осознанное ограничение, как в visible SQL).
