## Ещё не сделано — где fix может быть опасен

### P1.2 — `resolveMediaPath()` перед `RNFS.unlink` !!!

**Предложение:** в `deleteMessage` / `deleteChat` удалять файлы через `resolveMediaPath(relative)`.

| !!! Риск | Почему опасно |
|----------|----------------|
| **Двойной префix пути** | Если в `payload.uri` или `avatar_path` когда‑нибудь окажется уже абсolute path (`/data/...`) или `file://...` (старый бэкап, баг импорта, ручная правка БД), `resolveMediaPath` склеит `DocumentDirectoryPath + absolute` → `unlink` промахнётся или попадёт не туда |
| **Удаление не‑файлового аватара** | `avatar_path` может быть **id иконки** (`isChatIconAvatar`), а не `media/avatars/...`. Слепой `unlink` после `resolveMediaPath` — некорректно |
| **Общий файл** | Один и тот же `media/...` теоретически может быть referenced из нескольких записей (редко, но при агрессивном unlink без refcount — потеря медиа у других сообщений) |

**Безопасный fix:** удалять только если путь начинается с `media/`; для absolute — `unlink` as-is; для icon-id — пропуск; опционально проверка `RNFS.exists` перед удалением.

### P1.3 — Реализовать snooze «15 мин» на AlarmScreen !!!

**Предложение:** по кнопке «Отложить · 15 мин» перепланировать будильник.

| !!! Рisk | Почему опасно |
|----------|----------------|
| **Дублирующиеся alarm** | Если не отменить текущий native alarm (`cancelAlarm`) перед новым `scheduleAlarm` — сработает дважды или в неожиданное время |
| **Потеря связи messageId** | Snooze может создать новый id / новую запись в SQLite vs обновление существующей — рассинхрон JS ↔ Android `AlarmStorage` |
| **Exact alarms / Doze** | На Android 12+ без разрешения snooze «молча» не сработает; UI снова соврёт пользователю |
| **Повторный full-screen** | Прямой `startActivity` + notification — риск двойного показа AlarmScreen (см. `docs/bugs/alarm-fullscreen-not-triggering.md`) |

**Безопасный fix:** сначала уточнить контракт с `AlarmReceiver.kt` (тот же `messageId`, +15 мин к `scheduledAt`, cancel → reschedule). Пока не готово — **убрать текст «15 мин»** безопаснее, чем полу‑реализация.

### P1.4 — Применять настройки после импорта без перезапуска !!!

**Предложение:** после `updateSettings` из импорта дернуть `setTheme` / `setAppLocale` в провайдерах.

| !!! Риск | Почему опасно |
|----------|----------------|
| **Partial `AppSettings`** | `importFromJSON` кастует `data.settings as AppSettings` без валидации. Вызов `updateSettings(partial)` ок, но `setAppLocale(invalid)` → `dictionaries[locale] === undefined` → **краш при любом `t.*`** |
| **Тема vs Android native** | `ThemeProvider.setTheme` синхронизирует `ThemeModule` на Android; импорт через raw `updateSettings` минует это — возможен flash / widget / status bar не в той теме |
| **Экраны с закешированным `t`** | Смена locale на лету не перемонтирует уже открытые экраны (ChatRoom, Scheduled) — смешение языков в одной сессии |

**Безопасный fix:** валидировать settings при импорте (`SUPPORTED_LOCALES`, `getTheme(id)`); после успеха вызывать публичные API провайдеров, не писать в БД напрямую минуя них.

### P1.5 — Добавить медиа в Google Drive backup !!!

**Предложение:** паритет с ZIP — грузить `media/` на Drive.

| !!! Риск | Почему опасно |
|----------|----------------|
| **OOM / таймаут** | Большой ZIP в памяти на слабом Android; multipart upload без streaming |
| **Квота Drive / auth** | Обрыв на середине — пользователь думает, что бэкап полный, а медиа частично |
| **Конфликт имён** | Перезапись `licka-backup.json` vs отдельная папка медиа — нужна чёткая схема restore |
| **Приватность** | Медиа (голос, фото) в облаке без явного consent в UI |

**Безопасный fix:** отдельная фича с лимитом размера, прогрессом и явным «только JSON / JSON+медиа».

### P2.7 — try/catch внутри `importFromJSON`

| !!! Риск | Почему опасно |
|----------|----------------|
| **Проглатывание ошибок** | Если обернуть `JSON.parse` внутри и вернуть `null` вместо throw — callers могут не заметить сбой и показать «импорт успешен» с нулевой статистикой |

**Вывод:** лучше оставить throw и ловить на UI (как сейчас после P0 fix). Менять контракт `importFromJSON` — **опасно** без аудита всех callers.
